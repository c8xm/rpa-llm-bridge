# 设计说明

记录四个关键取舍，以及为什么不做另外那种实现。

## 1. 为什么是"统一 action 契约"而不是"每类自动化一套脚本"

浏览器脚本、桌面脚本、Office 脚本的差异只在下三层：定位元素的方式、输入的方式、读取的方式。往上一层的编排逻辑（重试、暂停、审计、参数化）是共用的。

所以 `BaseDriver` 只约定一件事：

```python
async def execute(self, action: str, params: dict) -> Any
```

`RecipeRunner` 不认识 Playwright，也不认识 pywinauto。新增驱动相当于新增一个类，执行器与策略层零改动。代价是丢掉了各框架的原生 API 细节——需要细节时，驱动内部照样可以自己写，只要把结果收敛成 `dict`。

## 2. 为什么策略集中在一处

早期做法是在每个工具函数里判断"这个按钮能不能点"。结果是判定标准分裂：浏览器那边拦了"购买"，桌面那边忘了拦"结算"，Office 那边根本没这个概念。

现在只有 `Policy` 一个判定点，任何驱动在执行前都必须过：

- `check_url()`：协议 + 白名单 + 同形域名
- `check_app()`：桌面应用白名单，空列表 = 全拒
- `check_input()`：敏感字段拦截
- `check_click()`：状态变更动作 → 拒绝或要求人工确认
- `check_step()`：执行前的静态检查

驱动内部仍可二次判定（例如元素文本只有运行时才知道），但复用的是同一套 `Policy` 实例。

## 3. 为什么人工闸门是"暂停 + 落盘"而不是"弹窗"

RPA 最危险的不是写错选择器，而是执行了无法回滚的动作。弹窗确认在无头场景下不可用，也无法审计。

因此采用状态机：

```text
running ──hitl/hit policy──▶ awaiting_human ──run_resume(approve)──▶ running ──▶ completed
```

暂停时把 `steps / index / results / vars` 整体写入 `artifacts/runs/<run_id>.json`。续跑从**暂停的那一步**开始执行（不是下一步），并带 `auto_approve=True`，否则会立刻再次暂停。这个细节在 `test_hitl_pauses_then_resume_executes` 里被固定下来。

## 4. 为什么不用元素 ref 的长期缓存

`list_page_elements` 会给元素打 `data-agentrpa-ref` 属性，返回 `e1/e2/...`。页面一导航或重渲染，这些 ref 就失效。

选择"短生命周期 + 显式失效"而不是"持久句柄"，原因是后者会让模型拿着过期引用做操作，失败信息还很难解释。现在约定是：点击或导航后重新 `list_page_elements`，ref 永远新鲜。代价是多一次调用，但换来的是可预测的失败模式。

## 5. 明确不做的三件事

| 不做 | 原因 |
|---|---|
| 注入反检测脚本、伪造 UA / 指纹 | 把风险转嫁给平台，也让"人工参与"的边界失效 |
| 绕过验证码、滑块、短信验证 | 这不是自动化问题，是身份问题 |
| 高频并发抓取 | 本项目的定位是"替人做可解释的重复操作"，不是爬虫框架 |

## 6. 测试策略

43 个单元测试全部不依赖外部进程：

- `test_policy.py`：白名单、同形域名、敏感字段、状态变更三种开关组合
- `test_runner.py`：成功、失败中止、跳过、重试计数、dry-run、模板渲染、未知驱动、策略拦截、状态落盘
- `test_recipes.py`：示例可加载、重复 id、非法 `on_error`、驱动继承、模板替换
- `test_audit.py`：写入、读取、按 key 脱敏、按 label 联动脱敏

`FakeDriver` 记录调用序列，因此"暂停后到底执行了哪几步"是被断言过的，不是靠人工观察。
